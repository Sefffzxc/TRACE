# Deploying the LBCA Monitoring System on Render

Four pieces, one blueprint file:

| Piece | Render type | What it is | Folder |
|---|---|---|---|
| `lbca-db` | PostgreSQL | the database | — |
| `lbca-ai` | Python web service | the trained risk model, inference only | `ai-service/` |
| `lbca-api` | Python web service | the FastAPI monitoring backend | `backend/` |
| `lbca-web` | Static site | the React app | `frontend/` |

---

## Read this first — the 30-day deadline

**A free Render Postgres expires 30 days after it is created.** You then get a
14-day grace period to move to a paid plan, and after that Render deletes the
database. Only one free Postgres can be active per workspace, and there are no
backups on the free plan.

For a thesis this is a scheduling problem, not a technical one:

- **Do not deploy the database months before your defence.** Deploy the three
  services whenever you like; create the database about a week before you need
  the live demo.
- **Write the expiry date down.** Render shows it on the database's page. Put it
  in your calendar with a week's warning.
- **Keep the seed reproducible.** `backend/seed.py` rebuilds the whole demo
  school from nothing, so losing the database costs you one command, not your
  data. That is the reason the seed exists as a script instead of being typed in
  by hand.
- If the demo must survive longer than 44 days, either upgrade the database to
  the cheapest paid plan for the defence month, or point `DATABASE_URL` at a
  free Postgres elsewhere (Neon and Supabase have free tiers that do not expire
  on a timer). Nothing in the code is Render-specific — `DATABASE_URL` is the
  only thing that changes.

Sources: [Render free tier](https://render.com/docs/free) ·
[the change from 90 to 30 days](https://render.com/changelog/free-postgresql-instances-now-expire-after-30-days-previously-90)

## Before you start

1. **Push this project to GitHub** (one repository, with `render.yaml` at the
   top level next to `backend/`, `frontend/` and `ai-service/`).

2. **Make sure the model file is committed.** The service is useless without it:

   ```bash
   git add -f ai-service/model/risk_model_v2.joblib ai-service/model/model_card_v2.json
   git status   # both files should be staged, ~1.7 MB total
   ```

   `.gitignore` does not exclude them, but joblib files are the kind of thing
   people gitignore out of habit — check rather than assume.

3. **Have your dataset's derived model ready to redeploy, not to retrain in
   production.** Retraining happens in Kaggle or locally; you commit the new
   `.joblib`, bump `MODEL_VERSION`, and redeploy `lbca-ai`. Nothing retrains on
   Render.

## Deploy

1. Render dashboard → **New** → **Blueprint** → pick the repository.
2. Render reads `render.yaml` and lists the four resources.
3. It prompts for **three** values. All three are public `.onrender.com`
   addresses:

   | Service | Key | What to paste |
   |---|---|---|
   | `lbca-api` | `ALLOWED_ORIGINS` | the static site's address, e.g. `lbca-web.onrender.com` |
   | `lbca-api` | `AI_SERVICE_URL` | the AI service's address, e.g. `lbca-ai.onrender.com` |
   | `lbca-web` | `VITE_API_URL` | the API's address, e.g. `lbca-api.onrender.com` |

   The `https://` is optional — both the backend and the frontend add it to a
   bare hostname. If Render renamed a service because the name was taken, use
   the name it actually gave you; each service's real URL is shown at the top of
   its own page.

   **Why these are typed in rather than wired automatically.** A blueprint can
   reference another service with `fromService: property: host`, and it is
   tempting. But that injects Render's **internal** hostname — the bare service
   name, no domain — which resolves only inside Render's private network. As
   `VITE_API_URL` that gives every browser request `ERR_NAME_NOT_RESOLVED`,
   because the value is read by the visitor's browser, not by Render. As
   `AI_SERVICE_URL` it points at a host that speaks http on the service's own
   port rather than https on 443. `ALLOWED_ORIGINS` has a further problem: the
   static site already needs the API's address, so pointing the API back at the
   site the same way would make the two depend on each other in a loop.

   None of those failures stop the deploy. They break quietly at runtime, which
   is why they are worth the thirty seconds of typing.

4. **Apply**. The first build takes 5–10 minutes. `lbca-ai` installs
   scikit-learn, which is the slow part.

Everything else is wired automatically:

- `DATABASE_URL` comes from the database. Render hands out a `postgres://` URL;
  `backend/app/core/config.py` rewrites it into the `postgresql+asyncpg://` form
  and moves `sslmode` into the driver's own TLS setting, so you never edit it.
- `SECRET_KEY` and `AI_SERVICE_TOKEN` are generated by Render. The token is
  generated on `lbca-ai` and read from there by `lbca-api`, so the shared secret
  exists in neither the repository nor this file.
- `AI_SERVICE_URL` and `VITE_API_URL` are filled from the service hostnames.
- Tables are created on the API's first start — there is no migration step.

### Check it worked

```bash
curl https://lbca-ai.onrender.com/health      # {"status":"ok","model_loaded":true,...}
curl https://lbca-ai.onrender.com/model-card  # metrics, features, and the limitations
curl https://lbca-api.onrender.com/health     # {"status":"ok"}
```

`model_loaded: false` means the `.joblib` did not make it into the repository,
or scikit-learn failed to install. The `error` field in that response says
which. Note that `/health` answers `200` even when the model failed to load —
deliberately, so Render starts the service and you can read the error, rather
than watching it restart in a loop with the reason hidden.

Then open the static site and **register**. The first account to register
becomes an approved administrator; every account after it is a teacher awaiting
approval. Sign-in on a new browser asks for a 6-digit code, which is shown on
screen while `DEBUG_OTP` is `true`.

## Loading the demo school

A fresh deployment has your administrator account and nothing else — no
students, no sections, no subjects. Two ways to fix that.

### Option A — run the seed from your own machine (recommended)

Free Render services have no shell, so the seed runs locally against the
database's **external** connection string.

1. Render → `lbca-db` → **Connections** → copy the **External Database URL**.
2. In `backend/`, with the virtual environment active:

   ```bash
   # macOS / Linux
   DATABASE_URL="<paste the external URL>" python seed.py --score

   # Windows PowerShell
   $env:DATABASE_URL="<paste the external URL>"; python seed.py --score
   ```

   `--score` then asks the deployed AI service to score every seeded record, so
   the demo opens with real model output rather than empty columns. For that to
   work, also set `AI_SERVICE_URL` and `AI_SERVICE_TOKEN` (copy the token from
   `lbca-ai` → Environment) in the same command. If you skip them, the script
   says how many records fell back to the rules — it never pretends the model
   answered.

3. `python seed.py --reset --score` wipes and rebuilds. Use it freely before the
   defence; never after you have entered real records.

**What the seed data is.** Invented students with invented class records,
generated by `assessment_record()` in `seed.py`. The names, the absences and the
scores are all synthetic. The *predictions* on them are genuine model output —
the demo calls the real service — but they are predictions about people who do
not exist. Say so if anyone asks what they are looking at, and never present a
seeded figure as a finding about LBCA.

### Option B — enter a class by hand

Class Management → add a school year, grade level, section and subjects → enrol
a few students → PACE Progress → **Class record** → type in absences and
assessment scores → Save. That is the real workflow, and going through it once
is worth more at a defence than a seeded database.

## Living with the free tier

**Services sleep.** A free web service stops after 15 minutes without traffic
and takes about a minute to wake. Consequences worth knowing before you stand
in front of a panel:

- The first page load after a quiet period is slow.
- The first PACE save after a quiet period usually falls back to the rule-based
  engine, because the API waits only 6 seconds for the model. The app labels
  those rows **rule-based** rather than hiding it, and the AI Risk Model page
  has a **Re-score records** button that re-runs them once the model is awake.
- So: **open the app two minutes before you present.** The AI Risk Model page
  and the Class record view both ping the model service on load specifically to
  wake it, and both show whether it answered.

**750 instance hours a month, shared.** Two web services that sleep normally fit
inside that. Two services kept permanently awake by an uptime pinger do not
(2 × 730 = 1460 hours), and when the hours run out the services stop until the
next month. Do not point an uptime monitor at these.

**The static site does not consume instance hours** and never sleeps, which is
why the React app is a static site rather than a Node server.

## Before real student records go in

The deployment above is set up for a demo. Three things must change first, and
they are listed here because the data protection question comes up in defences:

1. **`DEBUG_OTP=false`.** Right now the two-factor code is shown on screen,
   because no mail server is connected. With that on, two-factor authentication
   is decoration. Wire up email delivery, then turn it off.
2. **A real `SECRET_KEY`** — Render generates one, so this is already handled;
   just never commit one.
3. **Backups.** The free database has none. Real records need a paid plan or a
   scheduled `pg_dump` you keep yourself.

And the point that matters most for the study itself: the model's own
limitations travel with it. `GET /model-card` returns them, the AI Risk Model
page prints them next to the metrics, and they are not optional decoration —
they are the conditions under which the numbers mean anything. In particular
the model has **not** been validated mid-quarter, so the system must not be
described as giving early warning weeks ahead of a failing grade.

## Updating things later

| What changed | What to do |
|---|---|
| Backend or frontend code | push to the branch; Render redeploys on commit |
| A retrained model | replace `ai-service/model/risk_model_v2.joblib`, bump `MODEL_VERSION` in `render.yaml`, push. Then **Re-score records** in the app so stored predictions carry the new version |
| The model only, without a redeploy | `curl -X POST -H "X-Service-Token: <token>" https://lbca-ai.onrender.com/reload` |
| Service renamed | update `ALLOWED_ORIGINS`, and rebuild `lbca-web` — `VITE_API_URL` is baked in at build time, so a restart is not enough |
| Database expired | create a new free Postgres, update `DATABASE_URL`, re-run the seed |

## When something is wrong

| Symptom | Cause |
|---|---|
| Browser console shows a CORS error, but `curl` on the API works | `ALLOWED_ORIGINS` does not match the static site's address |
| `ERR_NAME_NOT_RESOLVED` on a URL with no domain, like `https://lbca-api/api/...` | `VITE_API_URL` holds an internal hostname. Set it to the public `.onrender.com` address, then **redeploy** the static site — it is baked in at build time, so a restart is not enough |
| Every prediction says **rule-based** | the AI service is asleep, or `AI_SERVICE_TOKEN` differs between the two services. `GET /api/ai/status` says which |
| `/health` on the AI service says `model_loaded: false` | the `.joblib` is not in the repository, or scikit-learn failed to build. The `error` field says which |
| API returns 500 on every request | `DATABASE_URL` is wrong, or the database expired. Render's logs show the connection error |
| Predictions show **partial data** everywhere | the assessment columns are empty. Fill them in under PACE Progress → Class record. This is correct behaviour, not a bug: the model is telling you it is working with medians |
| The app worked yesterday and everything 404s today | free database expired. See the top of this file |
